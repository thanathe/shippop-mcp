# Treat Confirm as eventually consistent; reconcile via `tracking_purchase`, never retry Confirm

In practice SHIPPOP's `/confirm/` call sometimes times out (SHIPPOP accepted the request but never answered), or returns `status: true` with an empty `courier_tracking_code` that the courier assigns moments later. We therefore never report a Confirm as failed on timeout and never treat a missing Courier Tracking Code as an error. `confirm_purchase` always echoes every SHIPPOP Tracking Code (`SPxxxx`) from the Booking, and whenever the Confirm call did not return a clean, complete result — timeout, network error, HTTP 5xx, a non-JSON (HTML gateway) body, or a JSON answer with missing courier codes — it makes exactly one reconciliation call to `/tracking_purchase/`: `purchase_status: paid` → report confirmed (filling in any Courier Tracking Codes now present); `unpaid` → report not confirmed and that it is safe to call Confirm again; reconciliation itself failing → report `unknown` and instruct the user to verify in the SHIPPOP console before retrying. Courier Tracking Codes still missing after reconciliation are reported as pending, to be fetched later with `track_shipment` by SP code — except shipments the courier explicitly rejected in the Confirm result (`status:false` with a message), which are reported as rejected, never pending, because their code will never arrive. Automatic retry of Confirm on timeout was rejected because re-confirming an already-paid Purchase has undefined behaviour and could double-dispatch.
